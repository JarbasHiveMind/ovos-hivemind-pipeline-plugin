# AGENTS.md — `ovos-hivemind-pipeline-plugin`

Guidance for AI coding agents (and humans) working in this repository. Read it
fully before making changes. It encodes conventions that are not obvious from
the code and that, if ignored, produce work that will be rejected.

## Repo

An OVOS intent-pipeline plugin (`opm.pipeline` entry point,
`HiveMindPipeline`) that sits at a configurable position in the local OVOS
pipeline and, as a catch-all, forwards any utterance it reaches to a remote
[HiveMind-core](https://github.com/JarbasHiveMind/HiveMind-core) hub. The hub
answers with its own skills/agent; the reply is spoken locally (default mode)
or, in slave mode, the hub gets direct bus access. Part of the
[HiveMind](https://github.com/JarbasHiveMind) ecosystem — a protocol for
connecting satellite devices to a hub running
[OpenVoiceOS](https://github.com/OpenVoiceOS). Related repos:
[hivemind_bus_client](https://github.com/JarbasHiveMind/hivemind_bus_client)
(the wire client this plugin drives), `hivemind-core` (the hub), the
architecture docs (spec).

## Layout / build / test

- Package module: `ovos_hivemind_pipeline/`. Tests live in `tests/` (unit:
  `tests/test_pipeline_unit.py`; e2e: `tests/e2e/test_pipeline.py`, driven by
  `hivescope`, an in-process HiveMind topology simulator) — do not create a
  second test directory.
- Set up a throwaway environment inside your clone; never touch a shared venv:
  `python3 -m venv .venv && VIRTUAL_ENV=$PWD/.venv uv pip install -e ".[test]" --prerelease=allow`
- Run the suite in the foreground: `python3 -m pytest tests -q`. The e2e
  module spins up a simulated hub via `hivescope`/`hivemind-core` in-process —
  no live network hub needed, but it is slower than the unit tests.
- `uv`, never `pip`. If latest prereleases fail to install or resolve, that is
  a bug to FIX at the source, not to work around with a pin downgrade.

## Working agreement (org-wide law)

- **Git identity is always** `JarbasAi <jarbasai@mailfence.com>`. Never set a
  per-repo override.
- **Never push `dev` or `master`.** Work on a feature branch and open a
  **draft** PR into `dev`. A human merges. You do not merge your own PRs.
- **Never merge or modify `Release X → master` PRs.** They are the
  maintainer's stable-release mechanism, generated by automation.
- **One commit per PR** (squash before pushing). Conventional commits;
  `feat:` only for a user-visible new capability. `fix:`, `docs:`, `chore:`,
  `ci:` otherwise.
- **Disclose AI authorship.** Every PR/issue/comment an agent writes carries,
  at the top: `> 🤖 Auto-generated by <model> via Claude Code — NOT
  human-reviewed. Verify before acting.` PR bodies are plain human prose (3–6
  short paragraphs), no tables or section-symbol spray.
- **Never edit someone else's** issue, PR description, or comment. Add a
  comment instead; on your own PRs, edit the body rather than piling on
  comments.
- Keep durable text (README, docs, PR bodies, comments) timeless and
  standalone: no dates, no "currently/now/new", no meta-commentary about the
  edit itself.
- No scratch files, committed virtualenvs, `__pycache__`, `.pyc`,
  `.egg-info`, or build artifacts in a PR. `git show --stat` shows only
  intended files.

## Dependencies

- **Floor pins only** (`>=X.Y.Za1`), bumped when a feature or fix is actually
  needed — with a one-line comment saying why. No upper caps unless a
  specific released version is genuinely broken (say which and why).
  `requirements.txt` presently pins several deps unversioned
  (`ovos-translate-server-plugin`) or with only a floor; treat that as the
  baseline to preserve, not to weaken further.
- **No lockfiles, ever.** Target the latest alphas (`--prerelease=allow`).
- Version and dependency list are dynamic in `pyproject.toml`
  (`attr: ovos_hivemind_pipeline.version.__version__`, `requirements.txt`).
  Never install from git — depend on a published PyPI alpha.
- Apache-2.0. Do not add GPL/AGPL dependencies.

## Tests

- Adversarial by default. A regression test must **fail before the fix and
  pass after** — prove it by reverting only the source (`git apply -R`, never
  `git stash` across worktrees) and watching the test flip.
- Tests must be mutation-proof: gutting the feature must fail the test. A
  test that only asserts a mock was called, without asserting the real
  behaviour, is weak — note it.
- Never skip a test because an optional dependency is missing.
- CI green is permission to review, not to merge. A non-trivial change gets
  an adversarial review before it lands.

## Repo-specific rules

- This plugin does not hold or resolve HiveMind API keys itself — identity
  and auth are the `hivemind_bus_client`'s job (`hivemind-client
  set-identity` / `test-identity`). Do not add key storage, caching, or
  resolution logic here; if a change needs it, it almost certainly belongs
  upstream in `hivemind_bus_client` instead.
- `match()` is an unconditional catch-all: it always returns a match. It must
  stay last (or near-last) in the pipeline order by convention — do not add
  logic that makes it fire conditionally without also updating the README's
  pipeline-order guidance, since satellites depend on this plugin only
  catching what nothing else could.
- `slave_mode` gives the remote hub direct local-bus access (arbitrary
  message injection via `hive.send.downstream`) — treat any change here as
  auth/trust-boundary-adjacent even though the boundary itself lives in
  `hivemind_bus_client`, not in this repo.
- `pipeline_id` for this plugin is the `opm.pipeline` entry-point name
  (`ovos-hivemind-pipeline-plugin`); it is also the skill/intent identifier
  matched against elsewhere in the ecosystem — do not rename the entry point
  without checking every config example and downstream reference.
- Locale dialogs (`ovos_hivemind_pipeline/locale/<lang>/*.dialog`) must stay
  in parity across `en-us`, `fr-fr`, `nl-nl`, `pt-pt` — adding or renaming a
  dialog key in one locale means adding it in all four, not just `en-us`.
